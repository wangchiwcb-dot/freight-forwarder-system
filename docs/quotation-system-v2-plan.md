# 门到门散货与拼箱报价系统 V2 实现方案

日期：2026-10-26。状态：V2 数据库、计价服务、真实原表参考比价及规则维护已部署香港服务器。按用户最新要求开放公网 https://quote.omfreight.vip/，移除案例验证和独立原件页签；正式渠道规则仍待业务核实。最新部署与验证见 quotation-v2-server-operations.md。

用户已确认首版业务范围：以门到门散货、拼箱为主，海运、铁路、卡航、空运四种运输方式并列，不设置陆运父级分组；包含公司自有渠道和同行代理渠道。整柜、整车不是首版自动计价验收范围。所有输入报价均为成本价格；自有渠道采用内部结算价，可作为本公司采购成本参与比较。首版不超过 5 人使用，暂不接入登录或权限管理。

## 1. 业务目标与现状

目标：输入一票货，找出满足承运、目的地、服务及时间要求的渠道，按各自规则计算整票采购成本，并给出同一比较口径内的最低已核价结果。

现有项目可保留 React、Ant Design、路由、页面布局、来源详情及历史记录的交互。V2 数据模型已经保留代理、渠道、报价版本、价格档位和来源证据，并由独立计价服务统一计算规则。当前主要缺口是正式渠道规则仍需逐项复核。货品查询是单选属性，尚不足以表达一票多品名、多属性及逐箱计费。

本次重新设计关系模型和后端计价流程。现有经过核对的数据作为迁移来源，不能因成功导入新库就自动标成“可计算完整总价”。

最低价的准确含义：**当前已发布、在指定业务日期有效、满足本票条件、费用范围已核实的渠道中，同口径整票采购成本最低。** 如果仍有待询价渠道，页面明确列出数量，不宣称覆盖了全部代理的实际最低价。

## 2. 先分清业务对象

| 对象 | 含义 | 示例与约束 |
| --- | --- | --- |
| 供应商/代理 | 向本公司提供运输服务的一方；本公司自有渠道也有归属 | 自有、同行代理；同一代理可有多个渠道 |
| 渠道服务产品 | 代理实际提供的一项服务，具有稳定身份 | 美国海运普船、欧洲铁路包税到门、欧洲卡航；名称变更保留别名 |
| 主干运输方式 | 海运、铁路、卡航、空运 | 页面和数据库均按四种并列方式处理，不设置陆运父级；每种方式下可有多家代理和多个具体渠道 |
| 末端派送方式 | 卡车、快递、自提等 | 海运加快递派送仍属于海运渠道，不能分类为空运或快递主干 |
| 货品品类 | 产品本身的业务分类 | 服装、家具、食品、电子产品等，可扩展 |
| 货品属性 | 影响承运与费用的事实，可以同时存在 | 内置电池、配套电池、纯电池、带磁、液体、粉末、品牌等 |
| 货件/包装组 | 实际参与重量、尺寸和逐件附加费计算的单位 | 同箱规同重量的箱可合并为一个包装组；组内保存数量及每箱数据 |
| 报价发布版本 | 某渠道在一段业务有效期使用的价格、规则和服务口径组合 | 固定引用价格版本、规则版本、分区版本及来源；发布后不可原地改写 |

代理层面只能维护其明确声明的通用要求；“代理做海运”不能推导出其所有海运渠道均接带电，也不能因“敏感货可接”推导出纯电可接。

同一票货可有多个货品，每个货品可以同时带电、带磁。需要逐箱判断时，货品与包装组建立对应关系。无法确认哪些箱带电时，不按平均分摊猜测附加费。

## 3. 数据库结构

建议 PostgreSQL 作为主库。核心业务字段用明确的列、外键和约束；变化较多的规则条件与公式参数使用经过结构校验的 JSONB。JSONB 不承担所有数据关系，也不存任意可执行程序。

| 业务模块 | 建议表 | 保存的主要内容 |
| --- | --- | --- |
| 代理与渠道 | `providers`、`channels`、`channel_aliases` | 自有/代理、稳定渠道编号、主干方式、末端方式、状态、历史别名 |
| 地点资料 | `locations`、`location_aliases` | 国家、起运交仓点、城市、邮编、目的仓、地址类型、核实状态 |
| 代理分区 | `coverage_sets`、`coverage_members` | 按代理和版本维护覆盖、拒收、偏远等区域；包含仓码、邮编、邮编前缀及区间 |
| 服务口径 | `service_profiles` | 起止交接点、含提货/清关/派送与否、关税/VAT、税费支付方、费用承担方、贸易条款（如有）、参考时效口径 |
| 价格 | `tariff_versions`、`rate_lanes`、`rate_tiers` | 价格版本、起运点与目的分区、货品适用条件、单位、币种、阶梯与最低收费 |
| 规则 | `rule_sets`、`rules`、`rule_bindings` | 规则版本、条件、承运判断/计费公式/附加费动作、适用范围及明确的覆盖关系 |
| 发布组合 | `channel_releases`、`release_rules` | 渠道发布版本、业务有效区间、绑定的价格/服务/分区版本、最终适用规则及继承依据 |
| 原件与导入 | `source_files`、`import_batches`、`source_evidence`、`parser_profiles` | 原件摘要、解析模板版本、导入状态、工作表及单元格、备注原文、规则/价格的证据关系 |
| 复核 | `review_tasks` | 待核规则、价格冲突、解析覆盖缺口、影响的渠道及处理依据 |
| 比价记录 | `quote_requests`、`quote_runs`、`quote_run_items` | 询价输入快照、计算器版本、使用的发布版本、费用明细、结果及缺失字段 |
| 汇率 | `fx_rate_sets`、`fx_rates` | 经选定的汇率版本、币种对、适用日期与换算方向 |
| 管理 | `audit_logs` | 修改和发布记录；首版无账号与角色权限 |

这些是逻辑表及职责建议，具体建表字段在计费样本核对后冻结，不把表的数量当成验收标准。

关键关系：一个代理有多个渠道；一个渠道有多个不可变发布版本；每个发布版本引用固定的价格、服务和规则版本；价格按线路/分区展开，再按重量或体积等条件匹配档位。多份 Excel 可以共同构成一次发布，一个 Excel 也可以提供多个渠道的证据。

不要给每家代理建一套独立数据库或专属报价表。代理的差异通过记录、条件和配置表达；针对不同 Excel 的解析模板可以不同。

### 关键字段与约束

- `channel_releases`：`channel_id`、`tariff_version_id`、`service_profile_id`、`valid_from`、`valid_to`、`validity_event`、`status`、`pricing_readiness`、`revision`。`validity_event` 区分按交仓、出运等哪个业务日期取价。
- `rate_lanes`：起运地点、目标分区版本、适用货品条件、计价单位、币种及服务变体；不同税费或服务口径不能塞成一个不加区分的价格。
- `rate_tiers`：上下界及是否包含边界、价格、全量档位/分段累进方式、单询/不可用状态。重复或重叠档位在发布前解决；合法替代方案单独编号。
- `rules`：规则类型、条件结构、动作参数、费用代码、计费依据、包含状态、累加方式、互斥组、覆盖对象、证据及复核状态。
- 金额、费率、重量和体积使用十进制定点值；API 使用十进制字符串，后端使用十进制运算，避免浮点误差改变最低价排名。精度和最终舍入按业务规则确定。
- 日期分别保存报价发布日期、业务生效期、导入时间、系统修订时间。区间统一用前闭后开；原文“含截止当天”转成次日零点并保留证据。时间存带时区时间戳，界面按北京时间显示。
- 发布版本不能引用另一代理的分区或价格；使用复合外键/约束及发布事务校验。渠道覆盖相同且业务有效期重叠时，必须明确替代或独立服务变体，禁止按“最后上传”静默选取。
- 发布后修订创建新记录并关联被替代版本。历史比价继续引用原版本，可重放；紧急停收及撤销通过独立状态使当前查询立即排除。

## 4. 各代理规则如何执行

规则分三类：承运条件、计费数量规则、费用规则。运营人员使用中文表单维护，界面表达为“当……条件成立，拒收/加收/减免/按……计算”。实现使用有限、可验证的条件与公式类型；遇到未支持的新规则类型再扩展计算器。

以下仅为演示规则，不代表实际代理报价：

| 渠道 | 货物条件 | 系统动作 |
| --- | --- | --- |
| 代理 A 的海运渠道 | 内置电池且资料满足要求 | 允许承运，按该渠道约定计费重加收 0.5 元/kg |
| 代理 B 的海运渠道 | 含电池 | 拒收；低价也不进入可选渠道 |
| 代理 C 的海运渠道 | 内置电池 | 允许承运，带电费用已含在当前价格内 |
| 代理 D 的卡航渠道 | 单箱实重超过约定阈值 | 仅对触发条件的箱子收超重费 |
| 代理 E 的空运渠道 | 目的邮编落入本代理偏远区 | 按该代理分区版本和收费标准计费 |

一个附加费必须有明确状态：另收、已含、明确免收、不适用、待确认。“没有解析出附加费”不能等同于免收。渠道完整计价资格还要求其收费范围已核实，不能仅凭“所有已录入规则都算完了”就声称费用完整。

条件判断采用满足、不满足、资料不足三种结果。资料不足时返回具体缺失项，例如电池类型、单箱尺寸、目的邮编；不能把未知当成“不触发附加费”。

通用规则可从代理继承到渠道，再由具体报价、目的地或货品条件补充。覆盖必须显式关联被覆盖的规则；“更具体”本身不能消除另一项不同费用。通用带电费可以被某渠道的“带电已含”替代，但超长费与偏远费可以同时发生。

同级规则冲突、多个相互不可比较的特例同时命中、费用叠加关系不明时转待核。承运拒收优先；渠道例外必须有明确来源及复核记录，发布时解决，不能让一条一般性的“可接货”自动覆盖拒收。

发布时生成本版本的最终规则清单，保留继承、覆盖及来源关系；查询时直接读取固定清单，避免每次临时拼接，亦避免通用规则修改后改变历史报价。

## 5. 海运、空运、铁路与卡航计费

四种主干方式共用数据库和计算流程，各渠道选用自己的计费配置。不能简单规定“空运统一除以 6000、海运统一按方、铁路统一按公斤”。

首版计算器需要支持：

1. 按公斤、按立方、按件、按票计费，以及明确约定的重量/体积择大规则。
2. 实重与材积重取大、分泡比例、单件最低重量、整票最低重量/体积、最低金额。
3. 逐箱取大后求和与整票取大两种模式；尺寸、重量和金额的进位顺序分别配置。
4. 重量/体积阶梯，明确区分整票套用某档单价与分段累进。
5. 货品、超长、超重、超尺寸、偏远、住宅、燃油、旺季等条件费用。
6. 固定费用、按数量费用、百分比费用，以及各自最低额、最高额、互斥/叠加关系。
7. 百分比费用必须明确基数是基础运费、某些费用小计还是申报货值；依赖关系必须无循环。
8. 若业务原表存在首续重、重量进档择优等规则，仅在完整约定被核实时启用对应公式；不自行推定。

例如按方渠道只有在原报价明确约定时，才采用 `max(实际体积, 实重 / 密度换算系数, 最低计费体积)`。密度换算与密度超限拒收是两种规则，不能混为一谈。

税费分别保存关税、VAT、清关服务费、支付方与承担方；“包税”不只存一个布尔值。贸易条款名称不代替具体费用范围。需要 HS、货值或税率而资料不全的税费，标为待核。查验、仓租等事后偶发实报实销项目单独披露，在相同排除口径下比较正常运输成本。

现库沿用的“未写不包税时默认包税”是有历史依据的业务默认。迁移保留其默认标识和规则版本，不伪造为原表明确条款；新版本是否可完整比价仍按服务范围和税费核实结果判断。

## 6. 一票货如何找到最低价

输入分为常用项和按需补充项：

- 常用：交仓点、目的国家/仓库或邮编、地址类型、货品和属性、实重、体积、件数、预计交仓/出运日期、允许的运输方式、服务及税费要求。
- 按需：每箱重量与长宽高、包装组与货品对应关系、电池资料、申报货值、HS、最晚到货要求等。只有涉及这些条件的渠道要求补齐，但有未判断费用时不能列入完整总价排名。

计算顺序：

1. 按起运地、目的地、日期、主干方式、渠道启停状态筛出候选发布版本。
2. 检查全部货品的承运条件、目的地覆盖与限制；明确拒收则排除，条件未知则待核。
3. 检查交接范围、税费范围及时间要求是否可比较。时效保留起算节点和自然日/工作日口径，预计时效与历史实绩分开。
4. 按每个渠道规则计算计费重量/体积、进位和档位，再计算基础运费。
5. 计算所有适用费用、最低收费与封顶，保存每一项的数量、单价、币种、公式、命中条件和证据。
6. 不同币种保留原金额，用用户选定/公司维护的同一汇率版本换算比较币种；缺失或不适用的汇率使结果退出跨币种排名。
7. 在费用口径相同、条件已核实的全部候选中按整票成本排序，然后分页；提供全局与各运输方式内的最低已核价结果。

不得先按基础单价只取前十名/第一页再计算附加费，这可能漏掉真正更便宜的渠道。完整计算的候选结果构成一次固定比价运行，后续翻页继续使用同一运行与版本，避免更新途中排序漂移；重新查询获取新版本。

采购总成本包括本次服务范围内由公司承担的已知成本：渠道费用、公司另付的提货/转运等补齐项、适用税费，扣除有明确依据的优惠。按服务项目识别已包含内容，避免重复计费。起运交仓点不同的渠道须补齐转运成本才能混排；门到港与门到门也不能直接比较。

自有渠道与代理渠道采用相同的成本范围。用户已确认自有渠道报价为内部结算价，可以作为采购成本；记录为 `internal_settlement`，代理采购价记录为 `supplier_purchase`。两者均须核实包含的服务及附加费范围；内部结算价不自动意味着所有费用已含。销售加价与客户报价是后续独立模块，客户价不进入采购成本排序。

### 结果状态与费用展示

| 状态 | 页面表达 | 是否参加最低价 |
| --- | --- | --- |
| 完整可计价 | 整票成本、计费数量、费用明细、有效期与参考时效 | 在相同服务/税费范围内参加 |
| 部分可计价 | 已知费用小计 + 未确定项目 | 不参加完整总价排名 |
| 待询价/资料不足 | 缺失资料或需代理确认的条款 | 不参加 |
| 不可承运/暂停/过期 | 具体原因 | 不参加；可在原因区查看 |

演示：同一票 300 kg、1 CBM 的内置电池货，假设各渠道均已确认按 300 kg 计费，且交仓、派送和税费范围相同：

| 方案 | 基础运费 | 本票其他费用 | 可比总成本 |
| --- | ---: | ---: | ---: |
| 代理 A | 5.0 × 300 = 1500 元 | 带电费 150 元 + 操作费 80 元 | 1730 元 |
| 代理 B | 5.5 × 300 = 1650 元 | 明确已含 | 1650 元 |
| 自有渠道 | 5.2 × 300 = 1560 元 | 同口径内部成本已核定，明确无另收费 | 1560 元 |
| 代理 C | 标价 4.8 元/kg | 拒收该货品 | 不参与 |

结果应选自有渠道；代理间选择 B。演示数值不作为任何代理的真实价格。

## 7. 香港服务器与前端衔接

建议部署结构：现有 React 静态前端 + Nginx 同源入口 + Node.js/TypeScript API + PostgreSQL。Excel 解析作为后台任务运行，复用已有 Python 提取能力；任务状态先存 PostgreSQL，首版无需额外引入消息队列服务。若服务器为 Linux，可通过 Docker Compose 管理服务；具体资源额度和备份方案根据已购配置落实。

数据库负责版本、约束和候选检索；独立 TypeScript 计价模块作为唯一的权威计算器。前端展示后端结果；不继续维护一套 SQL 价格计算、另一套前端价格计算并要求两者长期同步。已有十进制工具和有效业务测试用例可以复用。

前端保留布局与主要组件，定向增加：多货品属性、包装组输入、海运/铁路/卡航/空运四项并列筛选、整票成本与缺失费用提示、费用明细、规则维护、上传复核和发布管理。服务端提供 `/api/v2/quotes/calculate` 等新版接口，返回 `runId`、结果状态、可比成本、明细、规则证据及缺失字段。当前仅维护 V2 页面及 `/api/v2` 接口。

用户已确认首版不超过 5 人使用，暂不接入登录或权限管理；查询、草稿及发布操作使用同一应用。保留操作时间、版本和变更内容记录。PostgreSQL 只对应用内部网络开放；公网通过已配置的 HTTPS 域名访问。

原 Excel 按摘要归档，数据库保存引用；数据库和原件均需设置独立于本机磁盘的备份并验证恢复。查询由 V2 API 返回并保存结果快照。

### 查询速度

- 按当前发布状态、国家、主干方式、起运点、有效区间和目标分区建立索引；当前报价与历史版本有清晰查询边界。
- 发布时生成可检索的渠道覆盖与最终规则清单，避免每次读取原始 Excel 或解析长备注。
- 批量加载候选价格/规则，按本票条件计算并全量排序；费用详情和原件按需读取。
- 如实测需要，再添加短期缓存。缓存键包括完整输入、权限范围、数据发布版本、计算器版本及汇率版本；报价到期、撤销与停收不得被缓存继续使用。
- 建议以实际导入量和团队并发制定“常用比价约 1–2 秒”的验收目标；这是待测试目标，不是已有性能结论。先测数据库筛选、计算和网络耗时，再决定是否需要 Redis 或独立任务服务。

## 8. 报价更新与导入

新报价流程：上传原件 → 根据代理模板提取 → 生成草稿 → 展示新旧价格/规则差异 → 复核缺项与冲突 → 事务发布整套版本。

每家代理可维护解析模板，但输出统一结构。模板记录表头映射、合并单元格、备注覆盖范围、分区附表及识别边界。价格、币种、单位、承运和费用均关联来源单元格或原文。自动提取不确定的内容形成待核任务；不能默认为普货、零附加费或完整包税。

文件摘要用于去重，幂等键还包含解析模板版本和导入上下文；同一原件可以在新模板下重新解析，但该动作是解析修订，不伪装成代理发布了新价格。部分价格更新必须明确变更范围，未受影响的渠道可以显式沿用旧版本，不能因为文件缺少某行就删除或沿用整张报价。

导入与验收顺序：

1. 备份 V2 数据库、原件与核对记录，盘点来源和未解决问题。
2. 建立代理、稳定渠道身份和地点映射，保留导入编号及全部来源；待确认渠道不强行合并。
3. 导入历史价格、档位、来源和已确认规则；原备注、未知状态和历史业务默认原样追溯。
4. 为高频渠道补齐服务范围、逐件计费、货品和附加费；按核实程度赋予完整/部分计价状态。
5. 基础价逐项核对原表；完整总价用人工复核样本或已核对结算单验证。
6. 测试环境验收通过后更新应用；保留 PostgreSQL 备份及上一应用发布目录，确保回退不丢失业务记录。

运输时效资料不属于当前 V2 前端和报价数据库范围；报价版本只保留自身的原表时效文字与来源证据。

## 9. 实施阶段与验收

**阶段一：业务样本与规则定稿。** 从现有原件选自有及多家代理的代表性渠道，覆盖四种主干方式、按公斤/按方、带电、尺寸附加费和偏远地区。形成“输入货物 → 可承运结果 → 应收费用”的人工核对案例，确定规则表达和服务口径。

**阶段二：数据库与计价核心。** 建新库、版本发布和规则解释器；先跑代表性案例，覆盖逐箱与整票取大、进位、档位边界、费用叠加、含费/免费/未知、税费和币种、版本生效/失效、停收及规则冲突。

**阶段三：导入管理与旧数据迁移。** 完成解析模板、草稿差异、复核发布及旧 ID 映射；核对价格和证据数量、金额、关联关系，以及各渠道规则覆盖程度。

**阶段四：前端接入与部署。** 接入新版查询和费用明细，完善后台维护，按本期决定不接账号和权限；验证全量排序后分页、同一比价运行的稳定性、缓存失效、备份恢复和实际并发。用户已要求先完成本地开发与部署包，香港服务器部署另行衔接。

业务验收至少包含：A 代理可接而 B 拒收；同货物多属性组合；有附加费、已含、免收、未知四种结果；按公斤与按方同票比较；不同交仓点需要补齐转运费；门到门服务/税费不一致不可混排；过期与停收不能胜出；所有候选计算后选出正确最低价；任一结果可追溯原件并用保存的版本重算。

开发资料和部署信息的准备顺序见 [V2 开发启动记录](quotation-v2-kickoff.md)。自有渠道使用内部结算价已确认；实际收费范围仍按原件与核对案例落实。服务器资料可以在部署阶段补齐，不阻塞本地开发。
